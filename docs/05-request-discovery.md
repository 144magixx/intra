# 05 · 从哪里找到接口，怎样变成可调用定义

本章面向第一次接触接口的人：先找出浏览器真正发了什么，再把证据整理成定义。
开发版已实现人工整理的 JSON 定义导入与本地登记；缺失方法、路径时只返回缺口报告。
构建入口和环境限制见[开发版状态](11-runtime-status.md)，不自动解析 HAR/cURL 或观察网络。
统一约定见[设计基线](design-baseline.md)，阶段验收见[构建与验收](08-build-and-acceptance.md)。

## 1. 接口定义像一张请求说明书

浏览器里的“查询”按钮，通常会向某个地址发送 HTTP 请求。
定义要说清楚请求方法、路径、输入、成功条件和返回数据的位置。
例如“查第几页”是业务输入；“用谁的登录状态”是凭据选择，两者分开。
登记定义只是保存本地说明书，不会创建服务器接口，也不会修改服务端。
接口名称只是一条线索，不能单凭名字猜出请求细节。

可以把整个过程看成四步：

1. 收集文档、源码或实际请求，保留来源和观察时间。
2. 将能证实的事实写进草稿，未知项明确标注。
3. 审查参数、认证、成功判断和业务影响。
4. 在允许的环境验证，再把满足条件的定义标为 `verified`。

`draft` 表示仍有信息待确认；`verified` 表示特定证据支持这个版本。
`verified` 不承诺账号永远有权限，也不承诺服务器以后不会改接口。

## 2. 五种来源，各自能证明什么

| 来源 | 通常能获得 | 仍需核对 |
| --- | --- | --- |
| 接口文档 | 方法、路径、参数含义、响应结构 | 文档版本是否对应当前部署 |
| 前后端源码 | 路由、调用方式、组装参数的规则 | 基础地址、代理重写、运行时分支 |
| 浏览器复制的 cURL | 某次请求的方法、URL、头和正文 | 样本常量是否可变、命令内的秘密 |
| HAR 文件 | 一段网络记录中的请求与响应信息 | 是否包含正文、是否截断、是否脱敏 |
| 首次请求观察 | 启用观察后实际发生的请求 | 权限覆盖、正文缺失、业务语义 |

文档描述和源码实现不一致时，记录冲突，不自动选择更方便的一方。
cURL 与 HAR 中可能有 Cookie、Authorization、签名或个人信息。
导入时先隔离原始材料，再提取不含认证秘密的定义；不要把原件直接贴给 Agent。
HAR 有时能包含响应正文，但导出选项、缓存、格式或大小限制可能使正文缺失。
“导入了 HAR”不等于“已获得完整响应”。

截图可以证明页面出现过某个名称或字段；它不能补齐未展示的网络请求。
首次观察必须由用户明确限定站点、时段和操作，不自动浏览整个内网。
生产写操作的观察也需要对应授权；本轮不进行这种观察。

## 3. 两个相似名称，必须分别处理

| 项目 | `getPageAutoInterfaceList` | `getPageInterIdList` |
| --- | --- | --- |
| 证据 | 先前直接 HTTP 实验已验证 | 只有截图线索 |
| 服务 | `risk-api` | 尚不能据截图补全定义 |
| 方法 | `POST` | 未知 |
| 路径 | `/link_out/autoInterfaceManage/getPageAutoInterfaceList` | 未知 |
| 正文 | 包含 `pageNo`、`pageSize`、`params` | 未知 |
| 成功判断 | 业务 `code` 为字符串 `"200"` | 截图显示过字符串 `"200"`；完整成功规则未验证 |
| 列表位置 | `/data/listResult` | 截图显示 `/data/listResult`；非脚本回放证据 |
| 总数位置 | `/data/pageBean/totalRecord` | 截图显示 pageBean 和页面总数；完整字段未取证 |

已验证事实见[设计基线](design-baseline.md)，属于历史实验；开发版已有执行代码，但尚未用它重新验收真实内网请求。
左侧规范操作 ID 是 `risk-api.auto-interfaces.list`，见[操作示例](../examples/operations/risk-api.auto-interfaces.list.json)。
单次成功样本不证明 `params` 的全部约束或字段的可变规则，仍需补证。
不能把右侧名称替换进左侧路径，也不能照搬其 `POST` 或正文。
`getPageInterIdList` 当前只能作为 `draft` 线索记录，不提供可执行请求。
[operation schema](../schemas/operation.schema.json)要求 method/path 必填，因此先保留发现笔记，补证后再登记。
不要用占位路径绕过校验，让一个没有依据的定义进入调用列表。

## 4. 从样本到参数，需要再走一步

一次抓包中的 `pageNo=1` 只能证明这次发送了数字 1。
它本身不能证明该字段允许任意整数、默认从 1 开始或最大页是多少。
`params` 中出现某个 ID，也不能证明这个 ID 是调用者可自由替换的输入。
样本可能混合业务输入、固定协议值、账号标识、CSRF 值和一次性签名。

每次把常量提炼成参数，至少记录以下信息：

- 来源：哪份文档、哪段源码或哪组实际请求支持这项变化。
- 对照：在授权测试环境改变一个输入，观察哪个请求字段随之变化。
- 类型：数字、字符串、布尔值、数组或对象，不能仅按外观猜。
- 约束：必填、范围、枚举、缺省值，以及未知的边界。
- 影响：它是否改变目标账号、业务对象、查询范围或写入行为。

先限定证据支持的范围；只有一个样本时，保留固定值和待确认项。
身份字段不能因为“每次不同”就变成可任意指定的参数。
分页也需要证据：发现字段名含 `page`，并不授权自动翻页取全。

## 5. arguments 管输入，bindings 管放到哪里

JSON Schema 用来约束用户输入，例如“页码必须是正整数”。
`bindings` 把已校验的输入放入请求的 query 或 body。
下面只是合成示例片段，不是上述真实接口的完整定义，也不能直接登记：

```json
{
  "arguments": {
    "type": "object",
    "properties": { "pageNo": { "type": "integer", "minimum": 1 } },
    "required": ["pageNo"],
    "additionalProperties": false
  },
  "request": { "body": { "pageNo": 1 } },
  "bindings": [
    { "argument": "pageNo", "target": "body", "pointer": "/pageNo" }
  ]
}
```

例子中的最小值 1 是合成测试规则，不是对真实接口取值范围的推断。
输入 `{"pageNo":2}` 经校验后，把 body 中该位置替换成数字 2。
字符串 `"2"` 不应通过这个整数规则，更不应由模板悄悄转换类型。

这里的 pointer 使用 JSON Pointer，不是 JavaScript 表达式：

- `/params/name` 指对象内 `params` 下的 `name` 字段。
- `/filters/0/value` 指数组第一项中的 `value` 字段。
- 字段名中的 `~` 写成 `~0`，字段名中的 `/` 写成 `~1`。
- `bindings.target` 只允许 `query` 或 `body`，不是任意对象访问入口。
- 不运行 `eval`、函数、`${...}` 模板或用户输入的代码。

当前实现拒绝不存在的目标、危险对象键以及重复或父子重叠绑定。空指针允许替换整个query或body，但不能和同一目标上的其他绑定重叠；query仍须符合标量字段约束。
先复制请求模板，再按类型映射；不得因一次调用修改下一次调用的模板。
`/data/listResult` 这类响应指针只负责定位字段，不执行过滤或脚本。

## 6. 认证秘密不要混进接口说明书

service 定义保存基础地址、允许的 origin、Cookie 名称和认证判断规则。
operation 定义保存方法、路径、非秘密输入、响应规则和证据引用。
Cookie 值、Authorization 值、密码及一次性认证材料不进入这两种定义。
请求头也不能成为绕过入口：当前导入器拒绝认证头和识别出的敏感字段，不提供原始HAR/cURL自动清洗功能。
URL、query 和 body 同样可能含 token；不能只检查名为 Cookie 的字段。

调用时由服务、明确配对的浏览器 profile 和目标URL选择凭据，内部会话持有短生命周期标识 `credentialRef`。外部调用者不能凭此解析秘密；真实值只在受限 IPC、钥匙串和执行进程中使用，Agent只获得安全状态。
`storeId` 是 Cookie 存储区标识，不等于浏览器 profile 的身份。
凭据来自哪个 profile、哪个账号，必须在认证流程中单独核对。
接口定义通过审核，也不表示这个 profile 当前拥有可用登录态。
正常请求由 CLI 读取 Keychain 后直接通过 Node HTTP 发送；Native Host 负责浏览器同步。
桥接断线时，已缓存凭据仍可能有效；需要同步时才报告桥接缺口。

## 7. 浏览器观察能看到什么，不能看到什么

后续阶段可用 Chrome MV3 扩展提供显式开启的限域、限时观察。
`chrome.webRequest` 可提供请求事件、允许范围内的请求头/体，以及响应元数据。
响应元数据包括状态码、响应头、时序或错误等；不等于响应正文。
它不能直接抓取响应 JSON 全文，也不能据此自动推导返回字段结构。
响应正文需要 HAR 中实际存在的内容，或另选 DevTools/调试协议等能力。
采用调试协议属于独立设计与权限选择，不能伪装成 webRequest 自带能力。

`onBeforeRequest` 只捕获监听器启用且权限匹配之后到达该阶段的请求。
它不会补取启用前的请求、历史抓包或已发生的请求正文。
开启观察后，用户可能需要重新执行已授权的操作，才会出现新样本。
观察到其他阶段事件，也不能反推此前没拿到的 requestBody。

请求正文还需要正确的监听选项；文件、流、编码或浏览器限制可导致缺失。
请求头可见性受事件阶段、权限及 `extraHeaders` 等设置影响，不能承诺全部可见。
缺失的数据必须标记为“未捕获”，不能填空对象冒充真实正文。
扩展 service worker 会休眠；注册监听、恢复观察和报告缺口都需要单独验证。
观察窗口结束后停止收集；保存来源、授权范围和缺失项，不保存认证秘密。
被动观察到一个 POST 请求，不能证明该操作只读或允许自动重放。

## 8. 登记前的检查顺序

1. 核对 service 的基础地址和允许的 origin，防止把凭据送错站点。
2. 检查 method、path 和输入结构都有来源，未知项没有被自动猜补。
3. 验证 JSON Schema 与 JSON Pointer，拒绝动态代码和秘密字段。
4. 根据证据标记 `read`、`write` 或 `unknown`，不要按 HTTP 方法猜语义。
5. 写出 HTTP 状态和业务成功规则，保留业务码的原始类型。
6. 在合成环境验证输出，再按单独授权完成真实环境的只读验证。
7. 记录 `provenance.source`、证据引用和实际验证时间；verified必须有非空evidence引用列表和合法、非未来的带时区verifiedAt。校验格式不代表工具重新实测过该接口。

HTTP 200 只能说明 HTTP 层成功，业务仍可能拒绝请求或要求重新登录。
例如已验证的DevCloud接口可在未认证时返回 HTTP 200、业务码数字 304。
它不是 HTTP 状态 304，也不能推广成所有站点共用的认证规则。
响应字段缺失、类型变化或返回 HTML 时，应报告响应不匹配，不能制造空列表。

开发版命令如下；`intra` 是构建后 `node dist/apps/cli/src/main.js` 的简写。PATH/OPERATION/RESULT_PATH需换成实际值，调用还需已配对身份和适用凭据：

```bash

# 仅返回草稿报告，不自动登记。
intra api import --file PATH
# 审核后分别登记Service和Operation；重复ID需显式--replace。
intra api register --file PATH
intra api describe OPERATION
# 参数必须符合已登记操作；此处只是形式示意。
intra call OPERATION --profile work --args-json '{"pageNo":2}' --output RESULT_PATH
```

## 9. 当前边界

当前实现JSON草稿报告和本地登记，不自动读取文档、解析HAR/cURL、观察网络或将草稿升级为verified。缺少方法/路径时只有missing报告，没有虚构的可执行draft。新服务的登记也不会自动扩大扩展和宿主的站点白名单。
新定义如何落地、如何用合成服务验证，继续阅读[构建与验收](08-build-and-acceptance.md)。
未知接口保留未知，已验证实验保留原有范围，下一位实现者才能知道还需补什么证据。
