# 08 · 构建与验收：怎样证明它真的可用

> 当前已有开发版运行时，构建与合成测试结果见[开发版状态](11-runtime-status.md)。
> 下文验收场景是目标清单；未执行的真实环境项目仍不能标为通过。

## 1. 先分清构建、测试和验收

构建是把源码变成能运行或安装的产物；测试是检查某个输入是否得到预期结果。
验收则需要连同环境、过程和证据，判断一个使用场景是否真正成立。
文档检查通过不等于 CLI 能安装；宿主能连接也不等于业务账号已经认证。

先用合成数据和本地模拟服务测试。模拟服务是开发者控制的测试服务器，能稳定制造超时、跳转等情况。
合成 Cookie 是专门生成的假值，用于检查传输与泄漏；测试报告只记录是否匹配，不展示其值。
真实站点需另按明确授权验证指定只读操作；不拿真实写操作试验重放。

## 2. 按 M0 到 M4 推进

M 表示里程碑，即一组可以独立检查的交付目标。M1–M3描述第一版能力层次；当前都有开发版实现与合成测试，M2真实Chrome/Keychain及企业环境尚待验收，M4为后续能力。

| 阶段 | 要完成什么 | 进入下一阶段前需要的证据 |
| --- | --- | --- |
| M0 文档与契约 | 对齐文档、Schema、示例、状态与模块边界 | 离线检查结果；未实现项明确列出 |
| M1 合成 HTTP 服务 | 实现请求构造、响应判断、文件输出；用内部假凭据测试 | 本地服务记录请求次数、参数类型和输出字节数 |
| M2 扩展与 Keychain 桥 | Profile 配对、正向启动、受限 Socket、手动快照、钥匙串缓存 | 首次同步、断连、多账号隔离与关浏览器后的缓存用例 |
| M3 分类与恢复 | 区分认证、权限、网络和业务错误；限定刷新及重试 | 分类正确，刷新次数有界，写请求不重复执行 |
| M4 发现与增量 | 扩展文件导入和请求观察，增加有序 Cookie 变更同步 | 草稿证据完整；删除、重连、乱序和快照原子性测试 |

M0 可以整理已知接口定义；M4 的自动发现和请求观察不改变“Cookie 不能发现未知接口”的边界。
M2 不能把 NativeHost 当成永久守护进程；Chrome 关闭后，缓存请求仍由 CLI 读钥匙串并执行 HTTP。
M4 需要新验收才能发布，不应提前计入第一版已经具备的能力。

## 3. 当前构建与检查入口

需要 Node.js 22 或以上。在仓库根目录执行：

```bash
npm ci
npm run build
npm test
npm run check:docs
node dist/apps/cli/src/main.js --help
node dist/apps/cli/src/main.js doctor
```

`npm run build` 编译TypeScript，`npm test` 先构建再执行合成测试；它们不会自动安装扩展、注册宿主或访问真实业务。运行时使用AJV 2020-12和tough-cookie。[文档检查脚本](../tools/check-docs.mjs)仍可通过 `npm run check:docs` 单独运行，不需要安装依赖，也不验证Chrome登录、Keychain或真实HTTP业务。

正文中 `intra` 简写 `node dist/apps/cli/src/main.js`。doctor只检查运行环境和可发现的桥连接，不读Keychain；macOS状态为not-checked。实际auth sync/check前须登记服务与必要探针，完成浏览器桥安装、用户确认和Profile配对，命令见[规格契约](04-contracts.md)。

扩展清单可用 `node apps/extension/build.mjs` 显式生成；宿主启动器及清单按[宿主交付说明](../packaging/native-host/README.md)生成，需真实扩展ID和可执行启动器路径。生成不等于系统注册。首次真实Keychain访问还需macOS原生编译工具链构建Security.framework助手；这些真实环境步骤没有被合成测试代替。

## 4. 明确编号的验收场景

每项记录“未实现 / 未执行 / 通过 / 失败”，同时附预期、实际结果和证据路径。
以下共18项，是完整验收目标；已有合成覆盖与未验收项见[开发版状态](11-runtime-status.md)，不能把整张清单都标成已通过。

1. **契约与文档一致（M0）。** 检查已约定的相对链接、Schema 版本和合成消息示例。
   预期：缺失目标、非法示例或不支持的版本被明确报告；历史实验不能标成本项目运行测试。

2. **请求与响应类型正确（M1）。** 向本地服务发送带数字、布尔参数的已登记操作，并制造缺失字段。
   预期：JSON Pointer 映射保留类型；字符串业务码与数字业务码不混同，缺失列表字段不伪装成空结果。

3. **第一次同步成立（M2）。** 清空测试缓存，在指定 Profile 配对后，由扩展调用 `connectNative`。
   预期：Chrome 启动宿主，CLI 经 Socket 取快照、校验并原子写钥匙串；CLI 不反向唤起扩展。

4. **关闭浏览器仍可使用缓存（M2）。** 完成同步后关闭 Chrome，确保宿主也不可用，再调用本地测试服务。
   预期：CLI 直接读缓存并成功请求；模拟服务撤销会话后明确失败，不宣称能离线刷新登录。

5. **多个 Profile 不串账号（M2）。** 使用两个随机 Profile ID、相同 `storeId` 和不同测试账号。
   预期：别名只指向已配对连接；缓存隔离，重复身份冲突或账号变化时拒绝猜选，不静默合并。

6. **缺少 Cookie 有明确结果（M2）。** 缓存为空，扩展连接正常但目标范围内没有所需认证 Cookie。
   预期：返回 `COOKIE_NOT_FOUND` 或按契约归类的登录错误，退出码 3；不拿别的 Profile 凭据继续。

7. **302 按目标判断（M3）。** 分别返回普通业务跳转、已登记 SSO 登录跳转与未知目标。
   预期：只有站点规则确认的登录跳转才判认证失效；普通 302 不直接触发刷新，未知目标受允许来源规则限制。

8. **403 区分认证与权限（M3）。** 分别配置有效身份探针、认证失效探针和缺少可信探针的场景。
   预期：有效身份返回 `FORBIDDEN`、退出码 4；认证按规则处理；无法判断返回 `AUTH_STATE_UNDETERMINED`。

9. **HTTP 200 与业务 304 分开判断（M3）。** 模拟DevCloud已约定的 HTTP 200、业务码 304 响应。
   预期：按DevCloud规则识别认证问题，不报告成功；相同规则不得自动套用到其他服务。

10. **只读恢复次数有界（M3）。** 已审核 `semantics=read` 的操作首次认证失败，刷新后提供不同的新凭据。
    预期：最多同步一次、重放一次；凭据不变、同步失败或再次认证失败时停止，不形成循环。

11. **写操作与未知请求不重放（M3）。** 本地服务记下写入后断开连接；另测 raw 未知语义请求。
    预期：写入计数保持 1，响应丢失返回 `REQUEST_OUTCOME_UNKNOWN`、退出码 8；raw 不自动再次发送。

12. **跨 Origin 不转发原认证头（M1/M3）。** 设置从来源 A 到来源 B 的跳转，并分别测试 B 是否被允许。
    预期：不允许则停止；允许也要重新匹配凭据，不能原样转发 A 的 Cookie、Authorization 或 CSRF 头。

13. **Secure Cookie 不走 HTTP（M1/M2）。** 测试 HTTPS、普通 HTTP 和DevCloud精确 Origin 的 HTTP 例外。
    预期：HTTP 均收不到 Secure Cookie；DevCloud例外不传给其他站点，也不允许关闭 TLS 校验。

14. **分区 Cookie 不降级（M2）。** 提供带分区属性、目标认证所必需的合成 Cookie。
    预期：第一版返回 `PARTITIONED_COOKIE_UNSUPPORTED`；不删除分区属性后按普通 Cookie 发出。

15. **预算、完整性与分页真实（M1）。** 返回超过预算的正文、压缩正文和带下一页信息的分页响应。
    预期：按解码后实际字节限制，超限标 `.partial` 与 `complete=false`；不伪造完整 JSON，不自动请求下一页。

16. **秘密不进入命令输出（M1/M2/M3）。** 捕获 stdout、stderr、错误与摘要，并扫描合成秘密标记。
    预期：stdout 是单个 JSON 结果；两种输出及元数据均无 Cookie 值、认证头值、原始 Set-Cookie 或带票据 URL。

17. **网络与输出错误不冒充认证失败（M1/M3）。** 模拟 DNS/TLS 失败、正文超时、目标文件已存在和不可写。
    预期：分别按网络或输出错误退出，不刷新凭据、不覆盖已有结果；部分文件和完整性如实报告。

18. **发现与增量保留证据及顺序（M4）。** 导入缺少方法/路径的材料，并模拟变更删除、乱序和重连丢事件。
    预期：未知接口保持草稿；请求观察需限定范围，响应体另选来源；增量保留序列、删除语义及原子重连校准。

## 5. 怎样记录验收证据

每份记录至少包括：用例编号、代码版本、Node/Chrome 版本、合成或真实环境、预期和实际结果。
记录退出码、业务请求次数、同步次数、输出字节数及完整性；不要只留下“看起来成功”的描述。
同一用例至少检查成功与失败分支；并发刷新还要验证同一账号只有一个刷新者，等待有截止时间。

证据中不保存真实 Cookie、认证头或完整带票据 URL；业务文件按任务保存，摘要只保留必要字段。
真实业务响应的保存规则见[HTTP 与结果](07-http-and-results.md)，凭据隔离规则见[凭据](06-credentials.md)。
历史 WebCLI 实验只能证明当时特定接口可直接调用，不能代替上述桥接、缓存和恢复验收。

## 6. 什么时候可以写“可用”

当前可写“开发版运行时已实现，并有合成测试”；真实Chrome加载、宿主注册、Keychain访问和企业网络/站点调用完成对应验收后，才能扩大可用范围声明。
交付说明必须列出未覆盖站点、网络环境与后续能力，并链接本次真实执行的验收证据。
未执行的用例保持未执行，不用设计承诺、历史实验或文档检查代替结果。
更多事实与限制集中记录在[证据与决策](09-evidence-and-decisions.md)。
